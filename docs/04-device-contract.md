# Pillxai Dispenser 设备能力与兼容约定

本文件定义设备业务能力和当前机器的兼容约定。用户已确认：当前摆药机采用 **STM32 控制板**，现场机器通过 **HC-06 蓝牙串口**连接电脑，串口波特率 **115200**，本文件此前蒸馏的通信约定仍适用。用户表示此前已修改模块波特率，联调沿用 115200，不自动重新配置模块。新应用独立实现适配器；不读取、搜索或参考旧代码。机器使用情况有疑问时询问用户。

下述报文最初由文档蒸馏获得，协议适用性及正常摆药顺序已得到用户确认。2026-10-05 已使用交付包中的设备程序成功打开 HC-06 对应的 COM7；仅监听 8 秒，未收到数据，随后正常退出并释放端口，没有下发设备报文。初次检查仅证明串口可打开；随后用户现场摆药记录收到计数及 FINISH。2026-10-05 独立应答测试在现场已停止、应用已退出时，依次发送停转（`08`、对象 `00`、值 `0`）、退出药物（`00`）、开仓（`03`）：停转收到 ACK，退出收到 ACK 后 DONE，开仓收到 ACK、DONE；原始记录为 `.var/skip-probe-20261005.json`。测试没有下发数量矩阵，也没有修改正式业务数据。适配代码与报文测试通过也不代表机械位置、反馈时机和断线行为已通过实机验证。

## 设备向业务提供的能力

以下为**设计基线**，不规定方法名或网络接口。默认设备部署范围见 [00](00-scope-and-defaults.md)，业务状态转换以 R01–R15 为准。

| 能力 | 输入 | 可观察结果 |
| --- | --- | --- |
| 发现与连接 | 设备标识和连接位置 | 连接成功、失败原因、断开事件 |
| 提供能力描述 | 型号和已知配置 | 盘位数量、支持的计数范围、识别方式、反馈粒度 |
| 准备放盒 | 指定设备 | 开仓命令状态及可得的动作反馈 |
| 识别药盒 | 条码或 RFID 观察 | 标识、来源、在位变化、无效输入 |
| 执行药物批次 | 批次标识、目标位置数量、参数版本 | 接收确认、进度、完成或异常反馈 |
| 暂停与恢复 | 当前执行上下文 | 请求确认、后续执行状态 |
| 结束当前药物 | 当前执行上下文 | 跳过或终止请求结果，不自动表示已完成 |
| 清理剩余药物 | 当前设备 | 清理开始、结束及可得的回收计数 |
| 复位 | 当前设备 | 命令接收和复位完成分别表示 |
| 设置运行参数 | 参数名称、单位或设备刻度、数值 | 是否收到确认，设置适用范围 |
| 解除堵转 | 待处理电机或部件 | 本项请求结果，其余异常仍保留 |
| 收回轨道 | 已确认取盒的上下文 | 收仓命令与动作状态 |
| 采集诊断 | 当前设备和时间范围 | 原始事件、采样、连接信息和版本信息 |

设备没有自报能力或稳定编号时，可以由安装配置提供，必须注明来源。不得把主机端构造的任务标识伪称为硬件已回传的标识。

## 已确认的定位投料与计数行为

**用户已确认 Q04、Q05**：两个电机控制药盒行列位置；开始摆药后自动移至对应格子，工作人员可以直接投药，无需再次确认投料完成。机器自动计数掉入每格的药粒。半片由人工预切，设备按切好的半片颗粒计数。

**用户已确认 Q04、Q05**：半片按每次服药均为半片的常见场景处理，不设计混合整片与半片的复杂投料。机器暂停后保留已有进度，恢复后继续当前批次。

**协议核对 Q14**：主机接收当前批次颗粒序号或累计计数；目标量来自已下发计划。所查 V1 解析没有逐格位置和实际数量字段，详细来源见下表后的进度说明。现阶段无需为此增加新的逐格上报协议。

## 已确认的执行命令顺序

首次放盒前先发送开仓命令，让工作人员能把药盒放到轨道上，再自动识别所属住民。开仓命令发送成功不等于已测得机械到位；识别通过后才进入以下逐药顺序。该前置步骤由用户于 2026-10-05 确认。

1. 首次摆药不先发送关仓命令。先发送当前处方药物条目的转盘、舵机参数，再发送该药的数量矩阵。
2. 数量矩阵使机器自动移动到第一个需要投料的位置；开始后工作人员可以投药，无需人工确认投料完成。
3. 当前药完成且本盘的药全部处理后，发送开仓命令。计数达到目标与机器完成反馈分别记录。
4. 工作人员换好下一盘并确认后，先发送下一药的参数，再发送其数量矩阵；不插入关仓命令。
5. 同盘继续下一药也是“该药参数 → 该药矩阵”。暂停恢复沿用保留进度的操作，不重新发送矩阵。
6. 全部药处理后先开仓取盒。工作人员实际取出药盒并确认后，发送关仓命令 `04`（完整报文 `AA BB 04 04 00`）收回轨道，不重发数量矩阵；串口发送失败保留取盒阶段供重试。该取盒时机由用户于 2026-10-05 现场测试后确认。

异常或跳过退出时，主机先发送停转并等 ACK，再发送 `00` 并等 ACK、DONE；退出 DONE 返回后才继续下一药或发送 `03` 开仓。独立测试每条命令后监听 5 秒用于分开观察应答，生产流程按反馈推进，不使用该固定延迟。该应答顺序已实测，活动药物中的完整跳过及机械退出仍需现场验收。

该正常摆药顺序来自用户对实际 STM32 机器的直接确认。开仓 ACK 是接收事实，人工换盘确认是现场事实，两者不互相替代。

## 边界职责

以下为**设计基线**。

- 业务层决定住民、处方、日期和数量；不依赖某个串口名、命令字节或报文文本。
- 设备适配层把“业务时段与位置”转换成机器地址，把设备反馈解释为事件；不能自行更改处方剂量。
- Windows 串口属于首版平台适配。后续 Android、网页端、iOS 可按各端需要增加相应连接适配，复用上述业务能力约定；处方和计划不依赖 Windows 的串口类型或窗口对象。没有设备连接能力的客户端仍可按权限提供资料管理与记录查询。
- 摄像头、标签 PDF 导出和摆药机是不同能力。摄像头故障不等于摆药机断开；PDF 导出失败不等于处方无效。新版不直接连接标签打印机。
- 每台设备独立保有当前命令与执行上下文，不能共用一个未区分设备的 ACK 或完成标记。
- 接收确认、动作完成、业务完成分别表达。完成反馈不能串到另一个设备或新的执行批次。
- 无法关联的迟到消息保留为诊断信息，不用于替当前任务结算。

## 现有传输方式

**用户已确认**：当前现场连接链路为“Windows 蓝牙虚拟 COM → HC-06 → STM32 UART”。HC-06 使用经典蓝牙串口服务 SPP，不采用 BLE GATT。Windows 为该服务提供虚拟 COM，本机程序通过普通串口接口收发，业务层与 STM32 报文无需另立蓝牙版本。[Windows 蓝牙驱动栈](https://learn.microsoft.com/en-us/windows-hardware/drivers/bluetooth/bluetooth-driver-stack)、[HC-06 模块资料](https://www.rajguruelectronics.com/Product/708/HC%2006%20TTL%20Bluetooth%20Module.pdf)。

本机程序使用 115200、8 数据位、无校验、1 停止位、无流控。HC-06 与 STM32 之间的 UART 波特率也必须匹配；电脑打开虚拟 COM 时填写 115200 不等于已修改模块 UART 配置。用户此前已调整波特率，当前按 115200 联调，不因部分模块资料列出出厂 9600 而改为 9600。只有实际反馈表明需要排查时，再确认模块配置；正常会话不发送 AT 命令，不修改固件或串口驱动。

Windows 配对后选择与 HC-06 对应的**出站串口**，由电脑发起连接；入站串口不用于当前 HC-06 会话。不能按串口列表顺序自动选第一个，也不能把其他蓝牙设备的串口当作摆药机。2026-10-05 本机观察到 HC-06 蓝牙地址 `002506011CB1`，与 COM7 的远端地址一致；COM10 是本机入站端口。COM7 是本次连接位置，不是通用默认值或设备永久身份，重新配对或更换电脑后须重新确认。

配对完成、串口打开、收到有效 STM32 反馈、命令产生预期结果分别记录。当前首版连接成功只表示端口已经打开，不能据此显示“协议已验证”。打开端口不自动发送摆药、复位、开仓或探测命令。无数据可能只是机器空闲，不凭空判定波特率错误；验证接收需要现场产生已确认会主动上报的反馈，验证发送需要核对用户操作后的 ACK 与相应结果。

蓝牙传输按字节流处理，一次读取可能只有半条反馈，也可能包含多条反馈。当前入站反馈以 LF 或 CRLF 结束，先缓存并按完整文本行解析；实际设备若使用其他结束方式，须以接收证据修正。出站发送原始二进制字节，不能转成十六进制文本，不能额外加入回车、换行或蓝牙包装字段。掉线后不自动重发数量矩阵，任务与现场进度按既有中断流程处理。

当前 Windows 枚举的是串口，不足以证明每个列出的端口都是真正摆药机。连接位置可变化，不应直接作为设备永久身份。扫描范围、轮询频率和旧超时数值属于旧实现配置，不是产品需求。

**用户已确认 Q07**：每台机器连接各自电脑，同一机构的多台电脑共享业务数据；本次不要求单电脑同时控制多台机器。设备协议会话由对应电脑负责，任务分配与结果在机构范围协调。

## 现有出站报文

以下为**已观察的主机端编码事实 E08**。

报文顺序：两个头字节 `AA BB`，一个命令字节，命令对应的载荷，两个校验字节。校验值为“命令字节与全部载荷字节之和，取低 16 位”，低字节先发。旧代码虽命名为 CRC，实际不是多项式 CRC16。

没有统一长度字段或任务编号字段。浮点参数以 4 字节小端形式发送；整数延迟以 4 字节无符号小端形式发送。

| 命令 | 字节 | 已观察的载荷 | 已观察用途或限制 |
| --- | --- | --- | --- |
| 跳过当前药物 | `00` | 无 | 本机实测收到 ACK 后再收到 DONE；用于确认退出当前摆药项，不代表摆药完成 |
| 摆锤复位 | `01` | 无 | 主机等待 ACK 后继续等待 DONE |
| 清药 | `02` | 无 | 主机等待 ACK 与 DONE，并可接收回收数量 |
| 开仓 | `03` | 无 | 本机实测收到 ACK、DONE；开仓请求和反馈分别留存，不等于已经测得机械位置 |
| 关仓 | `04` | 无 | 同上，ACK 不证明实际位置 |
| 药片矩阵 | `05` | 28 字节 | 四行七列，按行展开，每格一个无符号字节 |
| 光耦阈值 | `06` | 当前主路径未确认完整调用约定 | 有命令常量，不能据此承诺可用配置功能 |
| 光耦不响应期 | `07` | 当前主路径未确认完整调用约定 | 同上 |
| 电机与舵机设置 | `08` | 1 字节对象编号加 4 字节浮点数 | 对象 0 为转盘、1 为舵机；2 和 3 用于解除对应堵转，浮点为占位 |
| 电机停转延迟 | `09` | 当前主路径未确认完整调用约定 | 有常量，无完整业务能力证据 |
| ACK 常量 | `0A` | 未确认出站调用约定 | 代码中有该常量，不能据此声称主机用它进行请求应答式心跳 |
| 清药速度 | `0B` | 4 字节浮点数 | 主机有发送方法，现场用途待确认 |
| 清药延迟 | `0C` | 4 字节无符号整数 | 主机以毫秒描述该值 |

暂停在旧主机中编码为转盘值 0；恢复编码为转盘值 8。用户已确认暂停后保留进度并继续当前批次。数值 8 作为现有恢复操作的兼容编码保留，不将其解释为普通物理转速；固件内部实现不影响该业务规则已确认。

### 阀门舵机手动设置

2026-10-05 用户单独授权核查 V1 的舵机发送逻辑，范围限于这项设备事实；其余独立重写约束继续有效。核查结果：V1 手动滑块允许 `0.0–1.0`，释放后直接发送该浮点数，不换算为角度、百分比或脉宽。命令 `08`，对象编号 `01`，随后为 4 字节小端 float32，末尾为既有累加和校验。发送 `0.7` 的完整字节为 `AA BB 08 01 33 33 33 3F E1 00`。依据：V1 `UIManager.cs` 的滑块范围与释放回调、`DispenserController.cs` 的 `SetServoAngle`、`SerialProtocol.cs` 的浮点编码与封包。

V1 校准配置说明数值越小开口越大，常用默认值为 `0.7`；这描述设备刻度，不证明它对应多少物理角度。新版沿用 `0–1` 设备刻度与 `0.01` 手动步长，不标注“度”。实际端点开口和动作方向仍由现场确认。

界面停止调整约 400 毫秒后自动下发最新值，松开滑块立即下发；页面初次显示不下发，连续调整不逐帧发送。本机 `setGate` 接收任务标识、药物批次标识与数值，核对当前药物后仅发送舵机设置；不重发数量矩阵、不改变计数、暂停状态或原计划。命令写入串口与机械动作完成分别表达，目前显示“已下发，请核对现场”，不将 ACK 当作角度已测得。手动设置及来源保存为本次药物的事件；启动前调整会沿用于该药启动，下一药使用自身参数。当前批次手动值不自动覆盖中央处方参数。

## 矩阵与业务时间的分离

**已观察 E05、E08**：

- 数据为 4 × 7，28 字节，行优先。
- 当前实际赋值：行 0 为晚，行 1 为午，行 2 为早，行 3 为零。
- 列表示本次安排的第 1 至第 7 天；日志将其显示为周一至周日，但没有因此形成按星期对齐的编码逻辑。
- 当前按药物各自计算天数，再从第 0 列连续填入；协议本身不携带日历日期。
- 单字节可表达 0 至 255，表示能力不等于药格物理容量允许放 255 粒。

**设计基线**：业务计划使用真实日期与服药时段，设备配置使用位置映射。新适配器只负责已确认映射，不将所有设备永久限制成当前的四行七列。使用现有设备时单盘日期数必须符合七列容量。

**用户已确认 Q01、Q02**：当前物理药盒从上到下为早、午、晚，与 V1 实际使用一致；未来按机构调整时段位置，并支持第四格“睡前”。七列代表本次第 1 至第 7 天；一位住民通常统一准备一个周期，允许提前摆药。漏摆后可选择当天或次日开始，不向已摆好旧盒补加新药。

**设计基线**：新适配器依据机构位置配置填充已启用的行，不能永久将第四行清零。分盘开关只决定是否拆成两盘，不决定第四行是否启用。当前代码行号与物理位置的转换应独立配置，不能将物理从上到下直接等同于协议从行 0 到行 3。

**待补充**：实体列的左右方向和第四行的设备动作支持。第四格睡前用途及当前物理早午晚排列已确认，不再作为业务未决项；协议到实体的正确转换仍通过位置测试验证。

## 现有入站反馈

以下为**已观察的主机解析格式 E08**。反馈主要按文本行解析。

| 文本 | 主机解释 | 不应扩大推断的内容 |
| --- | --- | --- |
| `ACK` | 命令接收确认 | 药物已完成或机械已到位 |
| `DONE` | 退出当前药物、开仓、复位、清药等动作完成信号 | 当前住民整项任务完成 |
| `machine init` | 设备初始化反馈 | 之前任务已恢复或完成 |
| `machine_state:FINISH` | 当前等待中的药物完成反馈 | 每个药格都有独立实测证据 |
| `machine_state:CNT_ERR` | 计数异常 | 哪些具体药格正确或错误 |
| `pills out:N` | 出药计数 | 必然是当前主界面的进度来源 |
| `cleaned pills:N` | 清药回收计数 | 已摆入住民药盒的数量 |
| `UID:十六进制标识` | RFID 有卡，规范化后用于绑定查找 | 标签本身包含住民信息 |
| `NO CARD` | RFID 无卡 | 摄像头条码药盒已经取出 |
| `number:N,width:W` 或以空格分隔 | 光耦序号与脉宽 | 脉宽已经具有确认的物理单位 |
| `stalled:N` 或 `stallN` | 堵转编号 | 所有编号都已有业务处理分支 |

当前主流程使用光耦消息中的序号驱动进度。旧式 `lowerOpt pulse width:W` 的解析分支已经注释，不能因上层留有无序号回退代码就声称该报文仍被支持。

### 进度数据的来源

**已核对 E08**：

- 当前药物批次的已摆数量主要来自 `number:N,width:W` 中的 N，主流程直接将它用于进度显示，不把 W 当作数量。
- 协议也解析 `pills out:N` 作为累计出药计数；当前主界面主要使用前一条序号路径。
- 本批目标总数由软件对发送矩阵中的颗粒数求和得到，不需要机器再单独回传总目标。
- 进度展示为“已摆 N 颗／目标 T 颗”；例如矩阵合计 21 颗，收到 `number:9,width:20` 后显示 9／21。
- 现有解析没有行、列与该格实测数量的组合字段，不能仅据累计 N 生成逐格实测记录。业务完成仍由完成反馈判定，不由显示百分比单独判定。

这些是 V1 主机端已实现的协议理解，与用户描述的正常进度体验一致；未读取固件，不推定它内部没有逐格计数。

协议未携带执行任务身份，丢失 ACK 后设备是否已经执行、重复矩阵是否重启任务、FINISH 是否可能迟到，需要固件或实机补证。新软件不能通过内部编号自动解决硬件并未提供的信息。

## 条码和 RFID 兼容

**已观察 E02、E06**：旧标签通常为六位补零住民编号。主机也提取 `PID:` 或 `BOX:` 前缀后的内容；这只是兼容解析，`BOX:` 并不证明旧系统有独立药盒编号。代码还可分割竖线分隔内容。

RFID 以不超过 64 个十六进制字符表示，去除约定前缀、空白并转大写后用于匹配。一个住民可有多个有效绑定。

工作台统一显示“药盒识别”，开仓准备后后台自动启动摄像头条码读取，同时接收串口 RFID 反馈，不展示摄像头画面，不要求工作人员选择来源。RFID 的 `UID` 与摄像头的解码文本都进入同一归属核验；`NO CARD` 只清除 RFID 观察，不清除仍有效的摄像头结果。未绑定的 RFID 不阻止同盒有效条码核验，两个有效来源冲突则阻止开始。识别来源仍保留在记录中，用于追溯。

**用户已确认 Q06**：识别到所属住民即可，同一人可以有多个盒子，不要求另建实体药盒编号。

**设计基线**：兼容住民条码和 RFID 绑定，保留原始标识及来源；不能仅凭六位编号跨机构找人。若定义新标签格式，围绕住民识别与机构归属设计，不引入单盒用途和周期追踪要求。

**已观察 E09**：扫码取盒使用原来成功识别的摄像头；稳定无条码窗口在当前场景为 1.5 秒。RFID 取盒使用新的反馈并检查稳定无卡。旧说明中的 1 秒、注释中的 3 秒不作为现行事实。

没有读到条码与成功测得药盒已取出之间存在能力差别。首版按 R13 使用当前识别来源观察，观察失败允许人员实际取盒后人工确认。条码稳定窗口先以 1.5 秒作为该设备适配初值，经实机验证调整；RFID 必须采用本次取盒阶段的新反馈，其上报周期和稳定窗口在联调确定，不复用缓存无卡状态。

## 参数优化候选策略

以下为**已观察的现有候选策略 E10**，用于保存既有调试经验，不是对真实药物的通用物理规律。

- 有效脉宽范围在主流程中为 3 至 200，单位未由固件证实。
- 至少 7 个有效样本，正常完成且启用优化时，用中位数计算参数。
- 当前 Home 场景启用优化，默认电机值为 0.2、舵机值为 0.7。类内初始值却是关闭优化、电机 0.3；运行配置不能只读代码默认值。
- 设中位脉宽为 W，速度候选为 `0.15 + (W - 5) × 0.01`，限于 0.15 至 0.36。
- W 不超过 13 时，舵机候选为 `0.85 - (W - 5) × 0.02`；超过 13 时为 `0.69 - (W - 13) × 0.055`，限于 0.08 至 0.98。
- 有历史参数且本次未手动调节时，保留历史舵机值；有手动调节时先按历史值 70% 和公式值 30% 混合，若最终手动值比二者都小，再将混合值与手动值各取 50%。无历史且无手动值时采用公式候选。

**设计基线**：这些公式作为现有设备的带版本候选策略，与处方和界面解耦。首版候选配置采用至少 7 个有效样本、电机初值 0.2、舵机初值 0.7；该机型实机验证后才启用生产配置。手动改开口是设备调整，不改变计划颗数。

每份处方独立保存参数、版本处理及半片改整片的规则唯一见 [R14](02-workflows-and-rules.md#r14-每份处方独立的出药参数)。设备默认值和计算公式可共用，但学习结果仅属于对应处方药物条目，不跨处方共享。上述公式作为首版现有设备候选，默认学习开关见 B10，实机结果决定该设备配置能否用于生产。

## 打印能力兼容

**已观察 E03**：

- 直接标签打印通过本地精臣打印服务，默认耗材为 50 × 20 毫米，使用住民姓名、床号和 Code128 条码。
- PDF 标签为 22 × 22 毫米，A4 每页 8 列、12 行，共 96 个位置。

**用户已确认 Q15**：新版仅保留 A4 上 22 × 22 毫米标签的批量 PDF 导出；精臣 50 × 20 毫米直接打印仅作历史事实，不纳入新版接入。PDF 沿用每页 8 列、12 行的布局作为兼容基线，支持跨页。应用不要求本地打印服务，不依赖打印机连接即可导出；实际打印由 PDF 工具完成，导出成功不能标成实际打印成功。

## 联调时需要完成的确认

只需围绕实际设备补齐以下有限事项，不要求在本次文档工作中重写固件。

1. 确认 HC-06 出站端口与实际模块对应，收到完整可解析反馈；再核对一次明确操作的出站报文、ACK 和结果。配对或打开成功不能代替双向通信验证。用不同位置的可区分测试计划验证药盘方向、行列映射与日期对应。
2. 按已确认顺序验证参数下发、矩阵定位、开仓与暂停恢复；补齐跳过、清药的实际机械行为。
3. 核对 ACK、DONE、FINISH 的发送时机，以及重发命令的结果。
4. 确认光耦序号起点、重置时机、缺号含义、脉宽单位与实际计数粒度。
5. 确认取盒观察、RFID 上报频率、第二盘识别方式和打印耗材。

这些结果写回能力约定与验收案例，使以后更换前端或设备适配实现时无需回到旧应用找答案。
