# Pillxa Dispenser 旧版行为提取补充

本附录保存正文整理前提取的旧版行为，仅用于查证，不作为新版功能要求。新版范围和规则以 README 所列权威文档为准；来源文件定位见 90-evidence-and-decisions.md。

## 01-product-and-functions.md

**已观察**：当前操作方式是工作人员逐种药物投料，设备按计划摆放；工作人员负责换盘、取盒和异常核对。不能把“无需开发者监管”解释成“无需护理人员参与”。

**已观察**：旧后台支持账号登录、退出、用户名查询、账号新增编辑删除和密码修改。实际权限是用户管理、住民管理、处方管理、日志查看四项开关，未观察到完整的医生或护士角色工作流。[E01]

**已观察**：支持账号维护、密码更新和四类权限控制；重复用户名被拒绝。[E01]

**已观察**：维护姓名、床号、照片、编号；按姓名或床号搜索；从住民进入处方列表。新增与编辑时检查非空床号是否重复。[E02]

**已观察**：一个住民可绑定多个 RFID 标签；标签规范化为大写十六进制；旧系统禁止一个 UID 绑定两位住民。条码可表示住民编号。设备扫码或 RFID 均可完成身份识别。[E02、E06]

**已观察**：提供直接标签打印，输入住民和份数；可连接打印服务、选择打印机并反馈连接状态。另有按住民指定份数生成 A4 PDF 的功能。标签包含姓名、床号与编号条码。[E03]

**已观察**：按住民新增、修改、启停和删除药物条目，维护药名、规格说明、图片、早午晚数量、饭前饭后或随餐、开始日期、持续天数、长期服用标记。按住民、药名、床号检索。[E04]

**已观察**：按有效处方和已有摆药覆盖日期判断哪些住民需要摆药，显示住民卡片和待摆药种数；支持手动刷新和定期刷新，运行中暂停自动刷新。[E05]

**已观察**：逐药计算本次天数和早午晚数量，按餐食关系形成一盘或两盘；展示药名、规格、服法和天数。现有设备单次矩阵最多七列。[E05]

**已观察**：既可先选住民再核对药盒，也可放入药盒自动找到有待摆药需求的住民。开仓后开始识别；显示识别结果与计划，操作人员确认开始。存在身份不符、未绑定 RFID、两来源冲突、药盒更换和移除的处理分支。[E06]

**已观察**：按药依次配置设备并执行；展示当前药物、规格、图片、目标颗数、进度和下一种药物。需要第二盘时开仓，等待人工换盘确认后继续。[E07]

**已观察**：暂停和恢复、跳过当前药、计数异常核对后继续、堵转清理后解除、执行期间调节进药开口。跳过有“记为已分发”选项。[E07、E08]

**已观察**：全部药物处理后开仓，进入取盒阶段。条码药盒按原摄像头持续观察无条码状态；RFID 药盒等待人工确认并使用新的空仓上报。无法确认时显示重试入口。[E09]

**已观察**：设备发现、连接、断开、连接状态、转盘清药、摆锤复位、参数设置；Windows 串口为当前文档主线，Android 蓝牙实现仍存在。[E08]

**已观察**：正常完成后收集有效光耦样本，通过脉宽中位数估计下次参数；支持优化开关、缺省值、样本门槛和手动舵机调节。当前保存位置关联处方条目。[E10]

**已观察**：后台有摆药日志写入与查询能力、管理操作日志；设备端有逐药光耦 CSV 记录意图。未找到当前客户端向后台摆药日志入口写入的调用，且 CSV 写入代码存在未定义变量，不能称为完整可用闭环。[E11、E12]

**已观察**：业务服务地址、单次摆药天数、提前提醒天数可配置；默认单次七天、提醒阈值两天。存在手动刷新、快捷键、技术日志及开发诊断工具。[E13]

## 历史候选能力

这些能力有旧实现或界面痕迹，但与当前摆药生产目标不同。列出它们是为了保留需求记忆，不是默认要求首版全部重建。

| 能力 | 已观察范围 | 本轮处理 |
| --- | --- | --- |
| 摄像头数药与药片面积估计 | 背景采集、轮廓计数、参考药片标定；V1 接手说明称数药算法已弃用，主摆药流程改用光耦参数 | 历史候选，与药盒扫码分开；不要求重写完整视觉算法 |
| 送药排班 | V0 护士、护工管理，住民关联，时间段与按日期生成任务 | 历史候选，不与机器摆药任务共用状态含义 |
| 送药提醒与任务监控 | V0 Android 提醒、即将超时提示、完成时间与备注 | 历史候选，不能据此推定已具备可靠服药证明 |
| 拍照提交界面 | V0 存在拍照和确认界面；所查提交入口主要更新状态与备注，未确认图片上传闭环 | 待确认，不标记为完整已实现功能 |
| 桌面本地文件缓存与同步 | V0 Python 客户端有本地 CSV 保存、拉取和上传路径 | 新版断网范围按 Q09：完成已开始任务并补传结果；不恢复整表覆盖或完整离线工作流 |
| Android 蓝牙部署 | V1 有兼容实现和调试入口 | Windows 以外是否保留待确认 |

以上依据见 E14。源码存在不代表当前现场仍在使用。

文中 E 编号的定位见 [依据与待决事项](90-evidence-and-decisions.md)。


## 02-workflows-and-rules.md

**已观察**：旧代码以处方开始日期、持续天数和最后一次摆药覆盖截止日期推算本次天数，默认最多七天、剩余覆盖不超过两天时提醒。旧字段中的 expiry 指已摆药覆盖截止日，不是药品有效期。[E05]

**已观察**：后台存储与 API 接收浮点剂量，现有表单按整数输入，设备计划构造时直接转整数，发送时转成单字节。[E04、E05、E08]

**已观察**：旧代码把饭前单独归类，把饭后、随餐和随时都归入另一个组。当有效处方中同时存在饭前组和后一组时，后一组进入第二盘，否则全部进入第一盘。这个检查发生在筛选本次需要摆药的条目之前。旧注释和页面上“饭前加随餐”的说法与这个判定不一致。[E05]

**已观察**：两种入口均存在。先选住民时要求标签匹配该住民；自动识别时根据标签查找有待摆药事项的住民。未绑定 RFID 不自动指定住民，摄像头仍可以识别。[E06]

**已观察**：旧流程按盘逐药执行，当前药物展示目标总量和下一药物信息；利用设备完成反馈结束本批次。[E07]

**已观察**：旧实现以电机参数命令实现暂停和恢复，恢复使用特殊数值 8。[E08]

**已观察**：跳过当前药后等待用户选择是否记为已分发；旧代码可直接推进覆盖日期。计数错误处理后也推进完整天数。[E07]

**已观察**：堵转反馈包含电机编号，当前流程处理 2、3 号电机；可存在多个待解除项。堵转等待期间暂停普通摆药超時計时，解除 ACK 后继续等待原任务反馈。计数错误则开仓供人工核对。[E07、E08]

**已观察**：旧流程发现设备断开时终止当前等待并清理内存中的计划和选择。未观察到可靠的跨进程恢复任务能力。[E07]

**已观察**：换盘需人工确认。结束时条码路径连续检测无条码，RFID 路径使用新的空仓上报并等待稳定状态。[E09]

**已观察**：当前主流程依据光耦脉宽和执行结果优化参数，并可记录最后一次手动开口调整；并非旧 README 描述的必须先拍药片测面积。[E10]

## 03-data-and-records.md

**已观察**：旧数据主要围绕住民、处方行、末次覆盖日期和分散日志组织；未观察到统一任务、处方版本和设备执行批次模型。参数直接保存在处方上，运行采样与后台业务日志相互分离。[E01、E04、E11、E12]

**已观察的采样意图**包括住民、处方、药品、盘号、目标颗数、样本序号、脉宽、相对时间、脉冲间隔、软件所设电机与舵机值、有效标记和执行结果。当前实现可靠性限制见 E12。
