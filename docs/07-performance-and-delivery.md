# Pillxai Dispenser 性能与交付基线

本文件给出本版设计目标与验收方法，不表示已经测试通过。当前技术和部署方案见 08，Agent 实施顺序见 09；实现通过可运行切片和实测校准，允许有依据地改进设计。

## 平台交付与演进

**用户最新确认，2026-10-18**：首发 Android 平板，直接连接 HC-06；Flutter 支持后续手机、平板、Windows 和 iOS。下述运行、性能、设备和安装目标针对 Android 平板首版。

技术方案与实现审查应确认：Flutter 界面、Python/FastAPI 服务和本机设备执行责任分离；设备、摄像头、文件与安装能力有平台适配边界；后续客户端访问同一机构数据与记录。

后续平台实施时再确定功能范围、连接方式、性能环境及安装发布机制。本次不要求交付其他平台安装包，首发由开发者下载安装包并手动安装，不承诺自动更新。

## 已确认规模

**用户已确认 Q16 及最新部署方式**：4 家养老院，每院约 200 位长者、最多 6 台摆药机同时工作，合计约 800 人、24 台；通常每台机器固定配一台终端，各机器处理不同长者。各院访问开发者维护的同一公网服务，平板由机构统一管理。

所有规模验证都同时验证机构隔离及本机执行归属，不能只用一个院的单线程列表测速。

## N01 可重复的测试负载

以下为设计测试数据，不是对现场处方或机器速度的估计。

| 项目 | 测试输入 |
| --- | --- |
| 当前资料 | 4 院 × 200 人，每人 10 个有效药物条目，合计 8,000 条 |
| 历史业务 | 每人 52 个历史任务，合计 41,600 个；每任务 10 个单盘药物批次，共 416,000 个批次 |
| 原始采样 | 每历史批次 50 条合成样本，共 20,800,000 条；包含重复、乱序及无效标记样例 |
| 正常并行 | 24 个独立设备会话，各每秒 5 条合成光耦消息，共 120 条/秒；同时写任务结果和各自处方参数版本 |
| 交互 | 每终端每 10 秒一次列表或详情查询，每分钟一次资料保存或计划生成，持续 30 分钟 |
| 持续运行 | 同并行事件量持续 8 小时，穿插换药、暂停、断网续摆及补传 |
| 附件与导出 | 每长者一张约 200 KB 的合成照片；一次导出 200 人各 1 张标签；另导出 100 万条采样 |

使用虚构资料，记录随机种子或固定数据集版本。测试生成与历史任务不影响生产数据。事件率可在实机测得峰值更高时上调，不据本基线宣称硬件每秒恰好出 5 粒。

客户端基准使用用户即将测试的实际 Android 平板，测试前记录型号、Android 版本、处理器、内存、屏幕、蓝牙及电源管理设置，不假定桌面 SSD 或 8 GB 内存。服务与数据存储合计起步参考 4 vCPU、16 GB 内存、SSD，最终记录用户公网服务器实配。基准网络往返延迟不超过 50 ms，并补充各院真实公网延迟、短时断网及重连结果；不将参考环境当成采购结论。

## N02 响应目标

P95 表示 95% 的测量不超过目标。除首开外，在 N01 正常并行负载下预热 5 分钟后测量；交互从用户动作到可用结果计时，排除人员等待和机械运动。

| 动作 | 首版设计目标 |
| --- | --- |
| 按钮、输入、切页的本地视觉响应 | P95 ≤ 100 ms；长操作即时显示处理中 |
| 待摆列表、长者搜索、处方详情、历史第一页 | P95 ≤ 1 s |
| 保存资料、处方或领取任务 | P95 ≤ 1 s；网络成功响应后状态可见 |
| 单人 10 药、7 天、最多两盘计划生成及预览 | P95 ≤ 500 ms，所需资料已读取 |
| 光耦消息到本机进度呈现 | P95 ≤ 200 ms，自本机收到报文起算 |
| 已上传结果在同院其他终端可见 | P95 ≤ 2 s，自中央确认接收到呈现 |
| 应用启动到可操作登录/工作入口 | P95 ≤ 5 s，参考环境，至少 20 次启动 |
| 200 张标签 PDF 生成 | ≤ 5 s，自资料就绪开始 |
| 100 万条原始采样导出 | ≤ 60 s，持续显示进度，不阻塞本机执行 |

远端机器离线时显示最后更新时间，不以“2 秒可见”虚构实时状态。硬件定位、单粒出药、等待人员及安装包公网下载时长不套用这些数字。

## N03 正确性与持续运行

- 24 台任务、计数、设备反馈、参数来源及机构归属不串线；并发领取只有一个成功。
- 模拟器发出的可确认样本与终端原始记录按身份核对，重复报文可留原文但不重复累计进度；未知/缺失必须可解释。
- 同一结果反复上传不增加任务、覆盖或样本事实数量，不触发硬件动作。
- 8 小时内无应用崩溃、未处理错误或导致超出 N02 的持续队列积压；运行结束后记录均可核对。记录峰值内存与积压变化，不用启动时内存代表长期状态。
- 单台断网后完成其已开始任务；另 23 台继续；联网补传正确，各处方参数互不影响，过时回传按 R14。
- 大导出、照片加载、另一终端更新不阻塞本机串口消息接收和进度更新。
- 首发平板切换其他应用和锁屏期间，已开始批次继续接收反馈并持久保存；至少完成代表性长任务，记录连接和系统电源状态。后台运行不自动跳过人员换药、换盘和核对步骤。
- 受控退出验证停转、现场确认和本次取消；系统强杀、崩溃及断电分别验证恢复核对和设备实际行为，不以应用进程消失证明机器已停止。

这些正确性要求优先于只追求平均耗时。实机动作的验收仍按 04 和 A23–A35，设备模拟不能替代实际位置与反馈验证。

## N04 发布、安装与更新

由开发者将已签名安装包手动装到未配置的机构 Android 平板后，经界面登录、授予必要权限、绑定本院 HC-06 并完成演示任务。日常工作人员不需要开发者在场或手工改配置文件。

发布记录至少有版本、发布说明、目标 Android 版本/架构、设备适配与服务兼容范围、签名、可下载包及完整性验证信息。开发者负责构建、发布、获取与手动安装，保存签名材料；首版可用简单发布工具，不必新增复杂发布管理平台。

开发者获取兼容的已发布版本，核验文件后等待任务结束、取盒完成且机器空闲再手动安装。不要求应用内下载图标、自动安装、强制更新或复杂分批策略。

升级验证保留机构绑定、连接设置、全部记录与待同步结果。安装失败保留或恢复一个可启动版本并显示重试方式；若涉及存储格式变化，恢复方案必须同时考虑数据格式，不能只替换程序文件宣称已恢复。

版本混用期间仍在执行的旧终端能完成任务并同步结果；必要兼容范围在每次发布中声明并测试。记录每个终端原版本、新版本、安装时间及结果。

## N05 备份与恢复

开发者负责现有公网服务器上的统一服务、数据库、附件备份和维护。设计默认：中央业务数据及已保存附件至少每日备份一次，部署目标为最多损失最近 24 小时中央新增数据、4 小时内恢复可用服务；这些是设计目标，实际恢复演练后才可声称达到。部署需 HTTPS、独立备份副本与恢复演练；具体服务器系统、域名和备份位置待部署时确认。

单机待同步结果位于本地持久存储，中央备份不声称包含尚未上传的数据。演练分别验证中央资料/附件恢复、终端未上传记录重启后补传，以及重复补传不重复执行。

长期原始数据不自动清理；备份不是业务历史的替代品。首版不设置自动删备份的功能，存储安排随实际容量在运维方案中说明。

## 完成交付的顺序

1. 业务与设备模拟：验证 05 的计划、身份、记录、同步和处方独立参数案例。
2. 单机真实流程：资料 → PDF 标签 → 识别 → 多药/分盘 → 暂停与异常 → 取盒 → 结果查询。
3. 多机多院：按 N01–N03 验证，并完成现有机型的适配验证。
4. 分别演练开发者在新平板手动安装、升级失败恢复和中央备份恢复，以及工作人员独立建资料、摆药、断网处理和查询。
5. 汇总已通过、未通过及尚未实测项；未通过不能以“文档已有案例”代替结果。

新系统明确不导入或兼容旧长者、处方、RFID 绑定、药品图片、历史结果与参数经验。演示使用新建虚构资料；上线重新建立真实资料与绑定。此决定不授权删除原系统或其备份。
