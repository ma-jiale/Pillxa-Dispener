# Pillxai Dispenser 首版范围与默认决策

本文件回答“这次做什么”和“未逐项指定时怎样工作”。用户确认优先；设计基线提供推进起点，允许 Agent 按第一性原理改进实现并验证结果，不要求不同 Agent 做出相同实现。

## 首版交付边界

**用户已确认的核心范围**：统一处方管理与机器控制；机构隔离；通常一终端固定一机器、多机各自处理不同长者；直接连接现有 HC-06；半片、餐食分盘、可配置时段位置；运行记录、新数据长期保存和批量 PDF 标签。首发由开发者下载安装包并手动安装。具体要求见 01–04。

**用户最新确认，2026-10-18**：采用 Flutter，后端 Python + FastAPI；首发 Android 平板，现已有可立即参与测试的平板。后续支持手机、平板、Windows 和 iOS，各端设备连接和生命周期分别验收。网页端不在当前首发范围。

**设计基线 B01**：首版面向 Android 平板直连 HC-06，完整交付“建资料 → 维护处方 → 预览计划 → 识别 → 逐药摆放 → 取盒 → 查询记录”。以下不进入首版任务清单：

- 送药排班、服药提醒、服药确认、拍照证明。
- 隔日规则、预设每日不同剂量、按需临时用药、非固体药物摆放、同药整半片混合投料。
- 库存采购、收费、诊断与处方推荐。
- Windows、手机专用布局、网页端与 iOS 的正式发布；视觉药粒计数、精臣直接打印。
- 旧长者资料、处方、RFID 绑定、药品图片、历史结果、参数经验和其他旧数据的迁移或兼容；首版自动更新。
- 实体盒编号与逐盒追踪、已完成旧盒追加新药、跨机器接力同一次任务。
- 完整离线建资料与开新任务、断电后无需现场核对的自动续摆。

普通处方修改（例如原来每次半片，以后改为整片）、睡前用药、人工核对未完成项仍在首版内。B01 是可实施默认范围；Q13 的额外功能询问尚未收到答复，不能将默认排除写成用户已明确拒绝。

## 平台演进要求

首版交付 Android 平板客户端，后续客户端按实际需要分阶段开发。首版设计应做到：

- 机构权限、处方、计划、参数归属、执行记录和同步约定与操作系统无关，后续各端沿用同一业务含义与服务接口。
- 页面交互与业务规则分开组织，不把规则仅放在页面生命周期、全局界面状态或蓝牙回调里。
- 设备连接、摄像头、文件保存、安装更新等平台能力通过明确的适配边界提供，Android 实现可以独立替换。
- 使用 Flutter 复用合适的业务与界面代码，同时按平板、手机和桌面的输入方式调整布局，不要求所有客户端共用全部平台代码。
- 后续各端具备哪些管理或机器控制功能、采用何种连接方式，在对应版本设计时确定；支持多端不等于各端必须具有完全相同的硬件能力。

首版验收包括 Android 平板的直接蓝牙连接、切换应用、锁屏、受控退出和异常中断。Windows、手机布局和 iOS 的设备连接与发布流程在各自阶段验收，不预先承诺 iOS 能直连 HC-06。

用户要求 UI 现代、简洁、有高级感，并已确认当前极简风格为唯一界面。侧边栏只有“处方管理”“摆药”“设置”，模块直接切换，不设返回页；移除底部方案栏和其他方案。主体采用白色或浅灰背景，允许灰色主背景配白色卡片，灰色用于区分层级。黑色仅为默认强调色，可由用户个性化调整；药品图片保留原本色彩。后续沿用这套风格完善处方管理及其余模块，用户提供的原型与参考图继续保留。已建立 `apps/client` Flutter 客户端交互预览，处方管理、摆药与设置使用内存演示数据。FastAPI、HC-06、后台生命周期和生产数据持久化尚未实现。信息层级和未保存内容保护见 06；实际运行与验证见[客户端说明](../apps/client/README.md)。后端、契约和设备验证可独立推进。

各院访问同一公网服务，由开发者负责部署、备份和维护；机构统一管理平板。代码须可读、精简，优先清晰命名、集中责任和显式依赖，避免无用抽象与重复实现。

## 默认设置

| 编号 | 设置 | 首次默认与保存位置 | 本次操作的变化 |
| --- | --- | --- | --- |
| B02 | 机构时区 | Asia/Shanghai，机构设置 | 计划按机构业务日期计算 |
| B03 | 一次准备天数、提醒阈值 | 7 天、剩余含当天不超过 2 天提醒；机构设置，天数可调整为 1–7 天 | 保存后持续沿用，日常自动生成，不在每次预览重新选择 |
| B04 | 首次或漏摆起点 | 当天；机构设置可切换次日 | 持续按设置计算；正常提前准备自动衔接已有覆盖，不要求逐次指定日期 |
| B05 | 餐食分盘 | 开启，沿用已确认分组；机构设置 | 预览可关闭，只作用于本次计划 |
| B06 | 物理时段位置 | 从上到下早、午、晚；睡前关闭；机构设置 | 院内管理员调整；布局变化需重新生成未开始计划 |
| B07 | 本机设备 | 一个终端绑定一台本院机器；终端设置 | 日常无需每次选择机器；其他机器仅供查看归属与进度 |
| B08 | 院内权限 | 新工作人员默认可查看本院资料、执行摆药、查看相关结果、导出标签 | 院内管理员可授予长者/处方维护、记录导出、设备维护与参数管理权限；无二次审批 |
| B09 | 床位 | 在本院所有已登记长者中，以去首尾空格的完整床位文本查重；可空 | 楼栋或病区重号时写入完整位置，如“A楼-201-1”；不另建床位管理系统 |
| B10 | 参数学习 | 新系统从新建档案开始；自动学习在新策略经实机验证前关闭，见 04 | 保存新采样与人工调整，不导入旧经验或默认启用旧公式 |
| B11 | 参数归属（用户已确认 Q10） | 每份处方内各药物条目独立保存，不共享 | 同药同规格也不跨处方互用；具体归属和保存规则见 R14 |
| B12 | 首发安装 | 开发者获取已签名 Android 安装包，在机构平板手动安装 | 升级在任务结束、药盒取出且本机空闲后进行；不承诺自动安装 |

**用户已确认 Q02**：覆盖日期的规则在设置中调整好后通常不变；日常由系统按设置与已有覆盖自动计算，预览用于核对。B03–B04 不提供逐次日期选择；设置修改影响新生成计划，不改写已开始任务。B05 的本次分盘开关仍与机构默认分开。相关设置、实际计算日期和本次分盘结果保存到计划快照，保留修改人及时间。

## 收敛后的业务决定

| 编号 | 决定 | 原因与权威规则 |
| --- | --- | --- |
| B13 | 已开始任务不转交另一台机器；异常在原任务现场核对、人工处理或结束 | 保持一人一次任务一台机器，见 R05、R12 |
| B14 | 新处方条目从设备默认值独立学习；同一条目的普通版本修改可延续自身经验 | 不复制其他处方已学习值；药物、规格或投料形态变化重新调整，见 R14 |
| B15 | 参数回传只更新原处方条目；版本或形态已变化时保存历史，不覆盖当前值 | 保留实际执行事实，刷新后重新调整；不设共享参数或合并工作台，见 R14 |
| B16 | 下一药物需点击“开始本药”；药物执行开始后可直接投料，无“投料完成”按钮 | 让换药边界明确，不改变自动定位、计数行为，见 R08 |
| B17 | 每次换盘必须重新识别通过，人员确认后继续；稳定检测取盒后自动收回轨道，失败人工确认 | 不增加独立盒号；识别与现场动作分别确认，见 R13 |
| B18 | 一般资料与处方在联网时维护，断网只继续已开始任务 | 与用户已确认的有限离线范围一致，见 R12 |

## 留给下一阶段的事项

- **额外范围**：Q13 的可选扩展未答复期间按 B01，不阻塞首版核心设计。
- **硬件验证**：行列物理映射、第四行、真实动作时序与反馈语义，按 04 的联调清单验证。不能靠文字推断已经支持。
- **架构实施**：08 已确认 Flutter + Python/FastAPI 及责任边界，09 给开发路线；当前已建立 Flutter GUI 预览，FastAPI、HC-06、后台生命周期和生产持久化尚未实现。工具链、运行入口与实际验证结果见[客户端说明](../apps/client/README.md)；生成器、平台通信、存储和签名安装继续在相应可运行切片中验证。旧数据明确不迁移、不兼容，不读取旧代码。
- **退出语义与实机边界**：切换应用和锁屏继续运行，主动关掉软件停止并取消本次。受控退出按 R12；普通关闭是否彻底删除全部记录、划掉最近任务是否视为主动关闭，以及系统强制停止/进程被杀时的机械停机保障，需结合用户操作定义和实机结果明确。
- **性能校准**：07 的负载与时延是本版设计目标，实测后才可称为达标。无需继续用“尚未给数字”搁置性能验收。
