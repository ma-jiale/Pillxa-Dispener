# Pillxa Dispenser 重写功能规格

本目录是养老院处方管理与摆药软件重写的业务依据。目标是：工作人员在一个应用里，把某位长者已确定的用药安排落实到药盒，并留下可追溯的结果；各院、各机器独立工作，日常使用无需开发者在场。

整理日期：2026 年 10 月 18 日。用户决定放弃本轮 Tauri 实现，使用 Flutter 重新开发。当前保留已整理的业务规则、验收目标和已确认设备事实。已建立 `apps/client` Flutter 客户端交互预览，采用用户确认的极简风格作为唯一界面；移除方案切换栏和其他方案，继续完善处方管理。处方管理、摆药与设置使用内存演示数据。FastAPI、HC-06、后台生命周期和生产数据持久化尚未实现。运行入口、实际验证结果和当前限制见[客户端说明](../apps/client/README.md)；预览不代表生产业务或真实设备能力已完成。此前 Windows 交付说明已移入本机归档，不再作为当前完成证据。

## 从事实出发

1. 处方表达需要，计划表达本次安排，记录表达实际发生的事。修改其中一个不能改写另外两个的历史。
2. 机器一次执行一位长者的一种药、一个药盘的数量矩阵；人员负责投料、换盘和现场处理。
3. 软件只记录可获得的事实：机器累计计数、完成反馈、人工确认分别保留，计划数量不能冒充逐格实测。
4. 机构决定数据归属，任务决定执行归属。一个任务绑定一台机器，各机器有独立进度。
5. 页面是操作入口，切页、切到其他应用和锁屏不终止任务；网络中断或上传失败不抹掉已发生结果。主动退出按 R12 停止、确认现场并取消本次；系统强杀属于异常中断。
6. 重写保留当前业务与已确认硬件约定，不继承旧类、数据库表、接口、页面结构或旧业务数据和参数经验。

## 规则效力

- **用户已确认**：来自用户直接回答，优先于设计默认值；来源用 Q 编号追溯。
- **设计基线**：可执行的起点，未声称用户逐条确认。Agent 可以改进页面组合、操作方式、模块结构和技术实现，以完成用户工作、保持业务含义和验证结果为依据，并直接更新受影响的定义与案例。
- **兼容事实**：来自主机端协议或旧配置的观察，仅在标明的设备范围有效；待联调项不能冒充已经验证。
- **候选范围**：不属于首版实现任务。纳入时再修改范围和验收。

用户已确认的业务要求与真实设备约束必须满足。其余设计可以改进，不要求不同 Agent 做出相同实现。普通工程选择自主完成。用户已授权项目目录内的工具链、依赖和缓存安装，无需逐项申请；系统环境、全局 PATH、注册表、驱动和服务变更仍须先申请。新决定直接修改权威规则、受影响的交互和案例，维持一套当前有效定义。

## 当前基线

首发 **Android 平板**，采用 **Flutter + Python/FastAPI**，平板直接连接 HC-06，通常一台终端固定一台机器。后续支持手机、平板、Windows 和 iOS；各端延续同一套机构权限、业务规则、数据语义与服务接口，硬件连接分别验证，见 [00](00-scope-and-defaults.md)。

首批 4 家养老院，每家约 200 位长者、最多 6 台机器同时工作，合计约 800 人、24 台机器；每台机器各配一台终端，同院共用机构数据。这是验收基线，不是产品容量上限。各院访问同一公网服务，由开发者负责部署、备份与维护，平板由机构统一管理，首发由开发者下载安装包并手动安装。

已确认的核心包括：时段位置可配置、可启用睡前格、七列最多表示本次七天、开始摆药确认弹窗可选择本次天数且默认 7 天、覆盖起点按长期保存的设置与已有覆盖自动计算、按日期和时段用彩色圆点可视化计划颗粒、可切换餐食分盘、人工预切半片、暂停续摆、断网完成已开始任务、换盘重新识别、稳定检测取盒后自动收回轨道、平台与院内账号分工、每份处方的药物条目独立保存参数且不共享、新数据长期保留（R12 显式“结束此次分药（不记录）”的删除例外除外）、仅批量 PDF 标签导出。

当前方向见 08：Flutter 界面、FastAPI 中央业务与本机执行保持清楚边界。新系统不迁移或兼容旧长者资料、处方、RFID 绑定、药品图片、历史结果和参数经验；重新建立资料和绑定。存储、执行核心实现、接口生成与具体依赖在可运行切片中验证。用户认可聚焦版的低信息密度与三个入口侧边栏；当前已建立“处方管理”“摆药”“设置”三个模块的内存交互预览，直接切换且不设返回页。用户已确认极简风格为唯一界面，去掉方案切换栏与其他方案，接下来重点完善处方管理。交互层级与最新颜色定义见 06，实施顺序见 09。
