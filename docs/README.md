# Pillxai Dispenser 重写功能规格

本目录是养老院处方管理与摆药软件重写的业务依据。目标是：工作人员在一个应用里，把某位住民已确定的用药安排落实到药盒，并留下可追溯的结果；各院、各机器独立工作，日常使用无需开发者在场。

整理日期：2026 年 10 月 18 日。已完成业务蒸馏、多轮确认、架构设计及 Windows 0.2.1 设备中断处理。可运行范围、首次使用及未实测项见 [Windows 首版交付](10-windows-first-edition.md)。设计目标与实际交付证据分别表达。

## 品牌素材

项目名称为 **Pillxai Dispenser**。[方形主标志](../assets/branding/pillxa-mark-rounded.png)采用圆角白底 PNG，只有圆角外部透明；[文字标志](../assets/branding/pillxa-wordmark.svg)保留原稿字形，收紧空白画布并按实际比例显示。素材保存在 assets/branding，使用说明见[品牌素材](../assets/branding/README.md)。

## 从事实出发

1. 处方表达需要，计划表达本次安排，记录表达实际发生的事。修改其中一个不能改写另外两个的历史。
2. 机器一次执行一位住民的一种药、一个药盘的数量矩阵；人员负责投料、换盘和现场处理。
3. 软件只记录可获得的事实：机器累计计数、完成反馈、人工确认分别保留，计划数量不能冒充逐格实测。
4. 机构决定数据归属，任务决定执行归属。一个任务绑定一台机器，各机器有独立进度。
5. 页面是操作入口，关闭页面、网络中断或上传失败都不抹掉已发生的摆药结果。
6. 重写保留业务与硬件约定，不继承旧类、数据库表、接口或页面结构。

## 规则效力

- **用户已确认**：来自用户直接回答，优先于设计默认值；来源用 Q 编号追溯。
- **设计基线**：可执行的起点，未声称用户逐条确认。Agent 可以改进页面组合、操作方式、模块结构和技术实现，以完成用户工作、保持业务含义和验证结果为依据，并直接更新受影响的定义与案例。
- **兼容事实**：来自主机端协议或旧配置的观察，仅在标明的设备范围有效；待联调项不能冒充已经验证。
- **候选范围**：不属于首版实现任务。纳入时再修改范围和验收。

用户已确认的业务要求与真实设备约束必须满足。其余设计可以改进，不要求不同 Agent 做出相同实现。普通工程选择自主完成。用户已授权项目目录内的工具链、依赖和缓存安装，无需逐项申请；系统环境、全局 PATH、注册表、驱动和服务变更仍须先申请。新决定直接修改权威规则、受影响的交互和案例，维持一套当前有效定义。

## 当前基线

首版开发 **Windows 版本**，同时在产品与架构设计中考虑后续 **Android、网页端及 iOS**。各端延续同一套机构权限、业务规则、数据语义与服务接口；平台范围和设计要求见 [00](00-scope-and-defaults.md)。

首批 4 家养老院，每家约 200 位住民、最多 6 台机器同时工作，合计约 800 人、24 台机器；每台机器各配一台电脑，同院共用机构数据。这是验收基线，不是产品容量上限。

已确认的核心包括：时段位置可配置、可启用睡前格、七列为本次七天、覆盖日期按长期保存的设置自动计算而非逐次选择、可切换餐食分盘、人工预切半片、暂停续摆、断网完成已开始任务、平台与院内账号分工、每份处方的药物条目独立保存参数且不共享、下载图标更新、全部数据长期保留、仅批量 PDF 标签导出。

当前技术方案见 08：独立 React 前端、Tauri Windows 外壳、TypeScript 中央后端、Rust 本机设备程序、PostgreSQL 与 SQLite。实施顺序见 09。具体库版本、表结构、接口生成和部署通过可运行切片验证；Agent 可以提出并验证更好的实现。
